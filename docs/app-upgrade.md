# Upgrading the App's Data

An **app upgrade program** is a small executable you ship with your app. It holds the app's own
upgrade code: database schema migrations, settings-format conversions, cache rebuilds. The installer
(first install, upgrade, repair, downgrade) and the in-app updater run it, without a window, every time
the installed files change. It can also clean up before an uninstall.

It is not an [install migration](migrations.md). Install migrations are compiled into the installer
(Native AOT, trimmed), deal with machine state around the app (an old copy, Run values, shortcuts), and
never run during an in-app update. An upgrade program is the app's own code, with the app's
dependencies (EF Core, a SQLite provider, your data model), on full .NET, and it runs on every
version change, in-app updates included.

| | Install migration | App upgrade program |
|---|---|---|
| Lives in | The installer project | The app's publish output (a release file) |
| Runs on | Installer runs only | Installer runs **and** in-app updates |
| Code | AOT-safe, installer APIs | Any .NET, the app's own libraries |
| For | Machine state around the app | The app's own data |

## How it works

1. The app's publish output contains the program (for example `App.Upgrade.exe`) and
   `instella-upgrade.json`, generated by an MSBuild property. Both are ordinary release files, so they
   are signed with the app's other files.
2. After the new files are in place, and while the operation can still roll back, Instella runs the
   program with the [launch contract](#the-launch-contract): the operation, the version before and
   after, the scope and the install folder.
3. Exit code 0 completes the operation. Anything else (a non-zero exit, a crash, the time limit) **rolls
   the install or update back** to the previous files, and it exits 15 (install) or 25 (update).

The program runs **at most once per operation**. A retry after a rollback is a new operation.

## Setting it up

Add a console project beside the app, reference `Instella.Sdk`, and make its `Main` one call:

```csharp
// App.Upgrade/Program.cs
return await InstellaUpgrade.RunAsync(args, UpgradeAsync, UninstallAsync);

static async Task UpgradeAsync(AppUpgradeContext context, IAppUpgradeProgress progress, CancellationToken ct) { … }
static async Task UninstallAsync(AppUpgradeContext context, CancellationToken ct) { … }   // optional
```

It is a separate executable, not the app with a flag: a tray or single-instance app can never be
started by accident, show UI or take its mutex.

In the **app's** project (the one whose publish output is the release), reference the upgrade project
so its exe lands in the app's publish output, and name it:

```xml
<PropertyGroup>
  <InstellaUpgradeProgram>App.Upgrade</InstellaUpgradeProgram>
  <!-- Optional: -->
  <InstellaUpgradeArguments>--db;data.db</InstellaUpgradeArguments>          <!-- extra arguments, ';'-separated -->
  <InstellaUpgradeTimeoutMinutes>30</InstellaUpgradeTimeoutMinutes>         <!-- 1 to 1440, default 30 -->
  <InstellaUpgradeHandlesUninstall>true</InstellaUpgradeHandlesUninstall>   <!-- default false -->
</PropertyGroup>
<ItemGroup>
  <PackageReference Include="Instella.Sdk" Version="…" />
  <ProjectReference Include="..\App.Upgrade\App.Upgrade.csproj" />
</ItemGroup>
```

`InstellaUpgradeProgram` is relative to the app's folder. `.exe` is added on Windows when missing and
dropped on Linux and macOS, so `App.Upgrade` works everywhere. Build errors `INSTELLA0301` to
`INSTELLA0303` reject an unusable path, time limit or uninstall flag. A publish whose output lacks the
program warns `INSTELLA0304`: every install and update of that release would fail.

The build writes `instella-upgrade.json` to the output and publish folders:

```json
{ "contractVersion": 1, "program": "App.Upgrade", "arguments": ["--db", "data.db"],
  "timeoutMinutes": 30, "handlesUninstall": true }
```

The upgrade program does not need to be AOT-compatible or trimmed. `Instella.Sdk` itself is.

## Worked example: an EF Core / SQLite schema upgrade

The app keeps its data in `%LOCALAPPDATA%\Example\example.db` and uses EF Core migrations. The upgrade
program applies pending migrations in one transaction, so a failure leaves the database as the old
version knew it.

```csharp
// Signatures only.
static async Task UpgradeAsync(AppUpgradeContext context, IAppUpgradeProgress progress, CancellationToken ct);
    // 1. context.IsDowngrade and the database has migrations the target version doesn't know:
    //    throw new AppUpgradeRefusedException("…")          → exit 2, the downgrade rolls back.
    // 2. progress.Report(10, "Opening the database");
    // 3. await using var db = new ExampleDbContext(DatabasePath(context.Scope));
    // 4. var pending = await db.Database.GetPendingMigrationsAsync(ct);
    // 5. For each pending migration: progress.Report(…, $"Migrating ({i} of {n})");
    // 6. await db.Database.MigrateAsync(ct);                 // EF records its own history
static string DatabasePath(AppUpgradeScope scope);         // per-user vs machine-wide data folder
static async Task UninstallAsync(AppUpgradeContext context, CancellationToken ct);
    // Optional: delete caches; keep user data unless your app promises otherwise.
```

EF Core records which migrations ran, so a repair (`--from` equal to `--to`) or a run after an
interrupted one finds nothing, or only the rest, to do. With SQLite, EF Core wraps each migration in a
transaction; if the app needs "all or nothing" across several migrations, copy the database file first
and restore it on failure.

## Rules for the program

- **Leave data usable by the old version when you fail.** When the program exits non-zero, times out or
  crashes, Instella puts the previous files back, and the previous version starts on your data. Either
  change nothing, or undo what you changed: one database transaction around the migration; write a new
  settings file beside the old one and rename it only at the end; rebuild a cache into a new folder.
  Never leave data behind that the old version cannot read.
- **Be restartable.** If the installer or updater is killed, or the machine loses power while the
  program runs, the next Instella run on the folder rolls the files back, and the next operation runs
  the program again with the same `--from`. The program is not told it was interrupted: an interrupted
  run looks like a failed one.
- **Track what has run yourself.** Instella keeps no list of upgrade steps. It passes the versions; your
  code decides (EF Core's migration history, a schema version in your settings file).
- **No UI and no input.** The program runs hidden, with stdin closed. Print progress (below) instead.
- **Rights.** It runs with the installer's or updater's rights: elevated for a machine-wide
  installation, the user's rights for a per-user one. For a machine-wide installation it therefore runs
  as the administrator who installed or updated, not as each user: per-user data (in each user's
  profile) is better upgraded by the app on its first start (`InstellaClient.IsPostUpdate`).
- **Processes it starts** end with it on Windows: the program runs in a job object that is closed after
  it exits, and ends it too if Instella itself dies.

## The launch contract

`InstellaUpgrade.RunAsync` handles the contract; apps without the SDK can implement it directly.
Version 1 is a frozen format ([compatibility.md](compatibility.md#formats-and-reader-rules)).

**Arguments**, in this order, followed by the declaration's `arguments`:

`--instella-upgrade | --instella-uninstall`, `--contract 1`, `--mode <mode>`, `--from <version|none>`,
`--to <version|none>`, `--scope user|machine`, `--install-path <folder>`, `--app-id <id>`

| Operation | Switch | `--mode` | `--from` | `--to` |
|---|---|---|---|---|
| First install | `--instella-upgrade` | `first-install` | `none` | the installer's version |
| Upgrade by an installer | `--instella-upgrade` | `upgrade` | the installed version | the installer's version |
| Downgrade (`--allow-downgrade`) | `--instella-upgrade` | `downgrade` | the installed (newer) version | the installer's version |
| Repair (installer or updater) | `--instella-upgrade` | `repair` | the installed version | the same version |
| In-app update | `--instella-upgrade` | `update` | the installed version | the release's version |
| Uninstall (`handlesUninstall`) | `--instella-uninstall` | `uninstall` | the installed version | `none` |

Versions are canonical (`1.2` is passed as `1.2.0`).

- **Working directory:** the install folder. **stdin:** closed. **Environment:** inherited, plus
  `INSTELLA_UPGRADE_CONTRACT=1`.
- **stdout:** a line `##instella progress <0-100> [text]` moves the progress bar and shows the text
  ("Upgrading your data…" until the program says otherwise). Every line is written to the install or
  update log; a malformed `##instella` line is logged as a warning and otherwise ignored.
- **stderr:** written to the log as warnings. The last stderr line is quoted in the failure message.
- **Log limits:** each line is cut at 4,096 characters, and at most 1 MiB per run is logged; later
  lines are counted, and progress lines are still read.
- **Exit codes:** `0` success. `1` failed. `2` refused (for example a downgrade the app does not
  support). `3` not understood (not a contract call, or a newer contract version than the program
  knows). Every non-zero code rolls back; 2 and 3 get their own log message.
- **Time limit:** `timeoutMinutes` (default 30). When it is reached the program's whole process tree is
  ended, and that is a failure. Nothing else cancels the program once it has started.

## Where it runs

**Install, upgrade, repair and downgrade.** In the install pipeline the built-in step `app-upgrade`
("Upgrading your data" on the progress page) runs right after `commit-transaction` and before every
custom Finalize step and the `AfterCommit` migrations. A failure rolls back the commit (exit 15).

- A custom step that is not a point of no return can run before it with `.Before("app-upgrade")`.
- A point of no return can never run before it, so a failed program can always roll the install back:
  `Build()` refuses `.PointOfNoReturn(…).Before("app-upgrade")`.
- **A custom Finalize step that fails after the program succeeded** rolls the files back, but not your
  data: the log warns that the previous version starts on data the new version upgraded. Keep Finalize
  steps that can fail before `app-upgrade`, or make the upgrade readable by the previous version.
- **Cancel stops working once `app-upgrade` starts.** A cancel after that point would put the previous
  files back over data the program already upgraded, so the install runs to its end. The window says
  so when Cancel is clicked.

**In-app updates.** The updater runs the program after moving the new files into place and before
completing the update. The window shows "Upgrading your data…" with the program's progress. A failure
rolls the update back (exit 25), and the app is not told about an update (no post-update marker).

**Uninstall.** With `handlesUninstall`, uninstall runs the program with `--instella-uninstall` first,
before uninstall migrations, `OnUninstall` hooks and Instella's own clean-up, while every file is still
there. A failure is logged and the uninstall continues. The program runs only if its bytes match the
installed manifest's record.

**A declaration Instella cannot honour** (a newer `contractVersion`, a program that is not one of the
app's files, an unusable path, not JSON) fails the install or update and rolls it back. The installation
stays on its working version; fix it by publishing a new release. There is no switch to skip the
program.

## Testing

- **The program:** create an `AppUpgradeContext`, turn it into arguments with `ToArguments()`, and call
  the overload of `InstellaUpgrade.RunAsync` that takes `TextWriter`s, then check the exit code and the
  progress lines:
  `InstellaUpgrade.RunAsync(context.ToArguments().ToArray(), UpgradeAsync, UninstallAsync, output, error, ct)`.
- **The installer:** `InstellaTestHarness.WhenProgramRuns(run => ProgramOutcome.Exit(0, "##instella progress 50 …"))`
  decides what the program does in `RunFullAsync` (`Exit`, `TimeOut()`, `CannotStart(…)`,
  `WithErrorOutput(…)`); the delegate can change the harness file system to simulate data.
  `ProgramRuns` lists every program started, with its arguments and working directory. Nothing is ever
  really started. `LogSink` holds the run's log, including the program's output.

## Installations from 0.1.0-rc.1 and rc.2

The updater is the installed stub, and an update never replaces it. Stubs from 0.1.0-rc.1 and rc.2
predate upgrade programs, so their in-app updates install the new files **without** running the
program. The next installer run on such an installation (an upgrade or a repair) runs it. This affects
pre-1.0 testers only.

## Limitations

- A custom Finalize step that fails after the program succeeded rolls back the files but not the data
  ([above](#where-it-runs)).
- On Linux and macOS (experimental) there is no job object: if the installer is killed, the program can
  outlive it.
- The program cannot show UI; interactive installs and updates show its progress text only.
